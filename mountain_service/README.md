# Private mountain weather service v0.3.3 (proposed)

The service requires Python 3.10+ on Linux and uses Python's standard library and SQLite. It listens on IPv4 loopback. Open the service URL for the private dashboard. Opening the repository’s static index directly runs the standalone simulation.

## Run in development

Start with an empty cache and no outbound requests. Use an owner-only directory outside the repository for the database and all backups.

```sh
state_dir=$(mktemp -d)
python -B -m mountain_service serve --db "$state_dir/mountain.sqlite"
```

The default URL is `http://127.0.0.1:8765`. Use `--port 0` for an ephemeral port. The service logs the selected port and sanitized refresh failures. The process holds an exclusive lock for its database. SIGTERM and Ctrl-C stop the listener and allow the collector to finish its current request.

For a one-shot check from an authorized development environment, use `python -B -m mountain_service probe ifs` and repeat for `hrdps`, `nelson_cs`, and `freezing_profile`. The command reports coverage and response metadata without printing readings or saving a cache. Use the synthetic regression suite for recurring development checks. Enable specific sources with repeated `--collect SOURCE` flags only for authorized private operation. Whitewater numerical measurements require explicit `--collect whitewater` and `--collect whitewater_weather` flags. Southridge and regional snow have no collection routes. The five Whitewater cameras are link-only. [Source validation and permissions](../DATA_SOURCES.md)

| Source key | Role | Poll interval | Fresh for |
| --- | --- | --- | --- |
| `ifs` | Primary ECMWF IFS HRES 9 km outlook, with 170 hours requested at lodge and Nelson | 3 hours | 9 hours from last successful retrieval |
| `hrdps` | Separate Canadian HRDPS Continental 2.5 km guidance, with 48 hours requested at both points | 3 hours | 9 hours from last successful retrieval |
| `nelson_cs` | ECCC measured valley air temperature, up to six recent features | 1 hour | 2 hours from observation time |
| `freezing_profile` | NOAA GFS 0.25° derived freezing levels near the lodge, with 72 hours requested | 6 hours | 12 hours from last successful retrieval |
| `whitewater` | Whitewater summit snow plot report, seven snowfall and depth fields | 2 hours | 30 hours from report update |
| `whitewater_weather` | Whitewater Base and Summit Top air temperature, wind speed and direction | 1 hour | 2 hours per station from observation time |
| `drivebc_whitewater` | North-facing JPEG still of Highway 6 at Whitewater Ski Hill Road | 20 minutes | Up to 45 minutes from the source update, subject to DriveBC status |

Forecast polls each use a single two-point request. With all products enabled, the nominal totals are 20 Open-Meteo HTTP requests and 24 SWOB requests per day before retries. Open-Meteo can count requests with many variables as multiple calls. The service polls independently of dashboard traffic. It uses an eight-second socket timeout, a body read deadline and a 1 MiB body limit. Network errors, timeouts, HTTP 408 and transient 5xx retry starting at one minute and double up to the normal interval. Invalid or empty data and other request errors wait until the normal interval. A 429, or an HTTP 503 with `Retry-After`, pauses all adapters for that provider until at least the requested time, with a five-minute minimum and a one-hour fallback if the header is unusable. A 401 or 403 stops that provider across restarts. Once access has been confirmed, stop the service and run `python -B -m mountain_service resume --db "$state_dir/mountain.sqlite" open-meteo` (or `eccc`, `drivebc` or `whitewater`). Due times and cooldowns persist across restarts.

Whitewater checks use fixed public URLs and the same bounded response handling as other adapters. No requests are made sooner than the source interval, including after transport errors and during manual batches. Shared provider spacing is at least 10 seconds, and provider blocks apply to both sources. These intervals cover the observed one-hour cache lifetime. Requests use the normal URLs without cache-busting.

The camera uses one roughly 1 KiB metadata response and downloads a still only when the source time advances or there is no cached frame. A newer source time with identical image bytes leaves the prior image age in place. The JPEG is capped at 256 KiB and dimensions at 1920 × 1080. Provider stop and cooldown rules apply. Other camera failures wait for the normal interval. At 20-minute intervals, the measured 60 KiB stills use about 4.2 MiB/day of upstream image bandwidth if every check has a new frame. At the 15-minute manual minimum, the corresponding upper estimate is 5.6 MiB/day. These estimates exclude HTTP overhead. The browser reuses the same private, versioned still in Overview, Webcams and the enlarged view. See the source review for the difference between the feed update and the image watermark. ## Local API v1

Direct requests must address `127.0.0.1` or `localhost` at the bound port. For the reviewed private proxy, pass each canonical HTTP(S) origin with `--allow-origin`. The listener stays on loopback. The API compares the request's Host and any Origin with the configured browser origin and ignores forwarded identity headers. Dashboard assets and JSON use `Cache-Control: no-store`. Camera stills use private browser caching for up to five minutes. The service serves only the dashboard, its live script and the documented endpoints. The dashboard reads same-origin cached data on a timer. Network access requires separate approval and the proxy and access controls in the [Pi package](../deploy/pi/README.md).

- **`GET /`** serves the live dashboard using the same HTML as the static simulation. The service marks the page as private and includes the live script.
- **`GET /v1/refresh`** returns the current manual batch’s phase, per-source outcomes, remaining cooldown seconds and `weather_budget` (`limit`, `remaining` and UTC `resets_at`). Phases are `idle`, `queued`, `running`, `complete`, and `failed` (interrupted batch). A completed batch can contain individual failures or skips.
- **`POST /v1/refresh`** requires an exact same-origin `Origin` matching the `Host` and configured HTTP or HTTPS scheme, the `X-Mountain-Refresh: 1` header and an empty body with no transfer encoding. The service sends no CORS headers. A valid request returns 202 and queues a batch on the single scheduled worker. A concurrent manual request or disabled collection returns 409. The 60-second server-wide request cooldown returns 429 with `Retry-After`. An unavailable collector returns 503.

The scheduler checks each enabled source in order. A manual batch can advance a healthy Open-Meteo product at least 60 seconds after its last check, or the DriveBC still after at least 15 minutes. Nelson and the Whitewater station table keep their one-hour minimum. The Whitewater snow report keeps its two-hour minimum. Existing retry due times and provider controls take precedence. A named per-source outcome explains skips. During refresh and recoverable failures, the last usable snapshot keeps its original valid times.

SQLite persists a limit of six manual batches with early weather requests per UTC day. A batch is charged immediately before the first otherwise eligible early Open-Meteo request, including if the request fails. Multiple Open-Meteo products in one batch use the same daily slot. If a batch spans midnight, early requests after midnight require a slot on the new UTC day. Due checks and camera checks remain eligible when the early weather budget runs out. The 60-second global request cooldown and batch progress live in the running process. Checked times, provider state and the weather budget survive restarts.

Six full manual batches add at most 18 early HTTP requests per UTC day. For budgeting, allow two call units each for the two-point IFS and HRDPS queries and round the GFS query’s 34 variables up to four units. This yields up to about 48 extra call units and about 48 units for the nominal scheduled workload per day before retries, far below the free tier’s 10,000/day, 5,000/hour and 600/minute limits. This is a per-database budget. Shared provider usage, retry traffic and one-shot probes also count toward provider limits. ECCC normally uses 24 SWOB requests/day with zero early checks, compared with the MSC policy’s 86,400/day contact threshold. [Open-Meteo pricing and call accounting](https://open-meteo.com/en/pricing) · [MSC usage policy](https://eccc-msc.github.io/open-data/usage-policy/readme_en/)

- **`/healthz`** returns 200 if SQLite is readable and the collector loop is healthy. Database or collector faults return 503. Check per-source state in the weather response for upstream health.
- **`/v1/weather`** returns `api_version`, UTC `as_of` and a `sources` object keyed by the weather entries in the table above plus `southridge`. Each entry has a label, kind, status and nullable data. Enabled sources also expose `checked_at`, `last_success_at`, `next_attempt_at`, `last_error`, `provider_state`, `age_seconds` and `age_basis`. Use each entry's `credit`, `link`, and `licence` when displaying data, including any provider notice carried by the observation. Disabled sources carry a reason. `unavailable` means there are no usable cached data for the relevant time. `fresh` and `stale` describe cached data. They can coexist with a recent refresh error. The dashboard labels stale sources and excludes their values from live indicators.
- **`/v1/weather` camera field** reports `disabled`, `unavailable`, `fresh` or `stale`. A usable still includes DriveBC’s feed update time and a versioned image path for **`/v1/cameras/drivebc_whitewater/<revision>.jpg`**. The path serves only the latest usable frame. The app keeps a stale frame visible with its label and stops serving it after six hours. A restart may leave the image unavailable until the next eligible source check.
- **`/v1/observations/nelson`** returns up to 288 retained readings in reverse valid-time order, breaking ties by most recent processing time. The response includes the station metadata and retention window. The same ordering determines the latest measurement in `/v1/weather`. This endpoint represents an intermittent recent cache and may have time gaps.

### Reading the data

- **Forecasts.** `data.points.lodge` and `data.points.nelson` each include requested and returned location, `times` (Unix seconds UTC) and matching `values` arrays. Metrics are `temperature_2m`, `snowfall` and `wind_speed_10m` with units in `data.units`. Coverage gives populated counts and first/last UTC valid times per metric from the current hour. Use the timestamps themselves to align models and sites. For any missing bin or field, JSON `null` represents missing data. `model_issued_at` stays null because the ordinary API supplies a continuously updated series without exact model issue time. `snapshot_retrieved_at` identifies the first retrieval of the current cached content and `last_success_at` identifies its latest successful check. Short-range coverage can end before 48 hours. A downscaled point remains model guidance.
- **Snow outlook.** `data.lodge_snowfall_windows` is derived from that source's modeled snowfall alone. Each bin ends at its valid hour. The object gives the first complete hour boundary, totals keyed by `24`, `48`, and `72`, and the maximum rolling 24-hour window over the next 72 complete hours. The earliest window wins a tie. Missing bins suppress affected totals, and an incomplete 72-hour set suppresses the rolling maximum. Zero is a valid forecast. A stale snapshot yields null windows. Actual snowfall comes from the separate `whitewater` source and only a fresh, validated 24-hour value drives its powder alert.
- **Whitewater observations.** The snow report contains `values` in centimetres, the plot elevation, `report_updated_at` and `source_time_label`. The weather source contains lodge and summit entries in `stations`, each with its own valid time, source time label, metrics and freshness. Unavailable metrics are null. The timestamp conversion assumes Whitewater local time. The top-level `measured_inversion` contains a fresh Nelson/lodge pair within 30 minutes or is null. Both valid times are included.
- **Measured observations.** `temperature_c`, feature ID, location, valid time `valid_at`, provider processing time `processed_at` and `retrieved_at` describe the accepted station feature. Same-time hourly and minute products retain their separate IDs. The provider and additional attribution notice are included when present.
- **Freezing levels.** `data.times` and `data.crossings` are parallel UTC hourly arrays. At each hour, `null` means insufficient or invalid profile geometry, and `[]` means no 0 °C crossing was detected in sampled, contiguous layers. Otherwise the array preserves every detected crossing in ascending height. A linearly interpolated crossing has equal `lower_m` and `upper_m`, while consecutive sampled temperatures of exactly 0 °C can have an altitude range. The adapter uses geopotential metres above sea level from one grid column, masks pressure samples at or below grid terrain, and never bridges missing levels or extrapolates beyond the available brackets. Coarse sampling can miss shallow layers and near-surface or high crossings. This is derived GFS guidance for the requested vicinity, separate from IFS, HRDPS, surface air temperature, the snowfall transition and measured snow cover.

## Retention and database recovery

SQLite uses WAL with full synchronous writes. Successful refreshes commit source data and scheduling/status together. Forecast and derived snapshots are stored only when normalized content changes. Keep seven days of snapshots by retrieval time, plus the current snapshot while it remains within seven days of a successful recheck. Keep only the most recent 48 hours of valid Nelson feature times from GeoMet. Whitewater retains only the latest normalized snapshot per source and prunes it after seven days without a successful recheck. Raw upstream HTML and resort images are excluded. This is a bounded recent cache, with no backfill or systematic archive collection. Pruning runs at startup and hourly. High-water database pages are reusable. Forecast histories are internal, while the API exposes the latest cache and recent observation window.

```sh
python -B -m mountain_service backup "$state_dir/mountain.sqlite" "$state_dir/backup.sqlite"
python -B -m mountain_service restore "$state_dir/backup.sqlite" "$state_dir/recovered.sqlite"
python -B -m mountain_service serve --db "$state_dir/recovered.sqlite" --port 8766
```

SQLite records camera check status and the weather budget. It keeps seven days of prior budget rows and the current day. Camera bytes live in memory and are excluded from SQLite and backups. The backup reads committed SQLite state, including committed WAL pages. It validates database identity, SQLite integrity and foreign keys, then publishes a standalone owner-only file. Restore copies and validates into a new file and refuses an existing destination or orphaned SQLite sidecars. Use the recovered path after verifying it by starting the service with collection off and checking the API. Preserve the previous database for rollback. Never copy only the raw database file while the service is writing. Keep backup copies private and expire them on a schedule that preserves the source retention limits. Production encrypted backup coverage, final paths, and recovery on the Pi need separate verification.

## Development checks

```sh
python -B -m unittest discover -s mountain_service/tests -v
python -B -m unittest discover -s poc/tests -v
CHROMIUM_PATH=/usr/bin/chromium python -B -m unittest discover -s tests -v
```

The service and browser suites use synthetic data over loopback and create temporary databases outside the repository. They cover malformed and missing data, forecast horizons, multiple crossings, transport and provider stops, stale cache, camera revisions and expiry, the daily budget across restart and UTC rollover, retention, and online backup/restore.

Set `NGINX_PATH` to a supported Nginx executable to also exercise the Pi proxy templates on development loopback with synthetic Host and Origin values. This check covers both listeners, rejected LAN sources, and refresh request validation. Tailscale, firewall and systemd runtime acceptance are Pi checks.
