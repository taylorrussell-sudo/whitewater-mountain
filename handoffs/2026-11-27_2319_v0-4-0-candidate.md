## Changes and decisions

- The five resort positions have original synthetic stills with selection, enlarged viewing and explicit loading, stale and unavailable states. The official gallery and per-camera still links are available. A browser requests only local fixtures when a resort camera is selected. The older resort tests include ambiguous clocks and a documented framing restriction. Written permission and a supported route are required before considering live display. [Camera research](../review/v0.4.0/whitewater-webcam-research.md)
- Powder Watch precedes the profile and cameras. Reported and forecast values use explicit text with solid and dashed accents. The wall Overview fits within 1920 × 1080 and the phone layout shows all five tabs together. Loading placeholders and stale labels distinguish the current data state. The fixture preview runs the actual UI and loopback API with temporary SQLite state and invented weather. [Before-and-after screenshots and launch instructions](../review/v0.4.0/README.md)
- The standard-library utility verifies a full approved Git SHA, staged file hashes and CLI version. It requires a private receipt from an operator-performed decrypt-and-restore drill and pins it to the archive bytes and installed configuration. It stages before stopping services, keeps the prior release, checks the backend and the active LAN edge, restores the prior release on activation failure, and publishes release metadata after successful checks. The automated path supports the documented standard layout and compatible SQLite releases. Power loss, an uncatchable kill and custom installations have manual recovery steps. [Pi upgrade and rollback](../deploy/pi/README.md#7-update-roll-back-or-remove)
- The seven collector integrations and their provider limits, the persisted weather budget and the SQLite schema carry forward from v0.3.4. Source opt-ins and private ingress settings live outside the release. The new CLI version updates the existing version string in the provider User-Agent. The existing DriveBC still remains eligible under its separate licence and cache policy. [Source notes](../DATA_SOURCES.md)

## Production acceptance sequence after owner approval

1. Complete the pending v0.3.4 checks on the physical wall and household phones. Verify the current encrypted configuration archive by decrypting and restoring its allowlisted contents and permissions into private scratch space. Confirm separate access to the recovery material. Record the known-good release, installed ingress and boot baseline privately.
2. Review the synthetic screenshots and run the fixture preview for fresh snowfall, changing freezing levels and unavailable cameras. Confirm wall readability, touch navigation and camera controls. Review the PR and approve an exact merged full SHA, application version and maintenance window.
3. Verify NVMe and recovery headroom, the active private ingress and the existing service and source opt-ins. Use the approved backup process and the upgrade preflight before starting activation. Keep the previous release, installed configuration and persistent SQLite state in place.
4. Execute the approved upgrade from the reviewed checkout. Check CLI version, backend and LAN health, the expected unit and boot states, and preserved data source settings. On an authorized LAN client, check dashboard access and refresh status with GET. Use a valid refresh POST only for an intended refresh. From a denied client, confirm ingress stays closed. Check the wall, phones and other Pi services and repeat the relevant startup and firewall checks after an approved reboot.
5. Verify a new encrypted configuration archive that contains the updated release identity and rollback reference. Monitor Pi RAM, CPU, disk and wall responsiveness through a representative collection cycle. If acceptance fails after the automatic checks pass, follow the runbook to restore the previous link and confirm health and ingress again. [Acceptance and reboot gates](../deploy/pi/README.md#8-acceptance-gates)
